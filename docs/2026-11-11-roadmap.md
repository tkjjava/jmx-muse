# Muse Bridge 后续路线图与细化分支

编制日期：2026-11-11（Asia/Shanghai）

**状态：规划文档，不代表已实施或已验收。** 本轮仅新增本文档，不修改业务代码、不运行测试、不重启服务、不执行上游请求。后续“继续”应结合用户当时授权判断是否进入实施；本文件本身不是部署或付费调用指令。

## 1. 总体方向

先把已经接通的聊天、媒体交付和暖池变成可验证、可恢复的稳定链路，再补客户端体验，最后考虑新能力。

推荐顺序：

1. **P0：明确基线与修复暖池生命周期缺口。** 确保身份变化、失败、取消和并发不会破坏连接归属。
2. **P1：完成聊天媒体验收。** 先查完成判定和错误语义，再验证上游取件、relay 透传和客户端实际展示。
3. **P2：补运行可观测性与发布流程。** 让复用、回收、取件失败和回滚有可靠证据。
4. **P3：按真实需求扩展能力。** 浏览器媒体提取、Space 导出体验等按使用场景推进；既有暂缓项保持暂缓。

不要把测试数量增加等同于可发布，也不要把一次 HTTP 200 等同于附件可下载或客户端可显示。

## 3. P0：稳定暖池与清理验证基线

### A1. 连接创建、失败和取消

**源码确认：** 初次连接路径先把槽位写入池，再直接等待 connect；该路径没有与重连失败路径相同的移除及关闭处理。重连失败捕获 Exception，取消语义需要单独验证。

拟议工作：

- 定义创建中、可用、租用中、空闲、关闭中的状态与合法转换。
- 首次连接失败或取消时，移除本次创建的槽位，并关闭本次持有的连接。
- 清理必须核对槽位身份，避免旧任务的异常处理移除后来创建的新槽位。
- 关闭和网络等待放在全局锁外；清理失败需可观测，但不覆盖原始错误。

分支：

- **连接成功：** 建立有效租用，结束后可归还为零引用空闲状态。
- **连接失败：** 本次槽位不残留，下一次可重新创建。
- **调用方取消：** 不残留后台接收任务或租用；账号锁最终释放。
- **清理期间出现新槽位：** 仅清理旧连接，新槽位不受影响。

验收：可确定复现上述四类场景；失败后无孤立槽位，取消后无本次遗留任务；其他账号不被慢连接阻塞。

### A2. 身份指纹与租用归属

**源码确认：** Cookie 指纹只包含各值的前 12 个字符；相同前缀、不同尾部不会区分。release 仅按账号查当前槽位；重复 acquire 出现多引用时主要记录警告。

拟议工作：

- 对完整 Cookie 集合做稳定摘要；不记录原值，摘要不作为认证凭据。
- 明确每次 acquire 返回的租用归属于哪个槽位/代次，release 只能归还自己的租用。
- 保留账号串行原则。优先拒绝重复占用或明确等待，不引入同账号多消费者共享游标。
- 审查连接失败后的引用归一逻辑：传输断开不能直接证明调用方已经不再持有租用。

分支：

- **身份未变化且空闲：** 正常复用。
- **Cookie 尾部变化、代理变化或模型变化：** 重新建立对应连接。
- **旧请求晚归还：** 不得减少新槽位的引用。
- **重复 close/release：** 幂等，不影响别的请求。
- **同账号并发 acquire：** 按明确策略处理，不能仅告警后共享游标。

验收：身份差异测试、旧租用晚归还测试、重复关闭测试，以及同账号争用测试均满足不变量。

### A3. TTL、关闭与管理操作

**已有能力：** 后台清扫已加入 lifespan。后续要验证生命周期，而不是再次声称“缺少定时器”。

拟议工作：

- 验证完全没有新请求时仍能回收；最大正常延迟由 TTL 加清扫间隔决定。
- 验证持有租用的连接不被空闲清扫关闭。
- 核对运行时开关与启动时清扫任务的关系，明确配置是否允许热切换。
- 核对账号删除、Cookie 更新、代理切换是否主动使对应槽位失效。
- 验证 lifespan 正常退出和异常退出均取消清扫任务并关闭池。
- 核对同一 driver 关闭后再次连接时，释放标记是否正确重置。

验收：使用可控时钟或事件同步，避免靠短 sleep 偶然通过；无请求条件下能观察到实际 close，而非只观察到清扫函数被调用。

### A4. 两个固定失败与测试警告

历史失败为 Noise 协议字符串长度断言，以及 int64 输入 2^63 的往返断言。另有测试夹具协程未等待警告。

处理顺序：

1. 分别确定协议定义和编码器约定，判定是实现问题还是测试预期错误。
2. 对 int64 明确合法范围与越界策略：拒绝越界或明确转换，不让测试默许未定义行为。
3. 保留能说明原问题的回归依据；不能为了绿色结果直接删除断言。
4. 修复异步夹具与真实接口不一致导致的警告。

分支：实现有错则修实现；测试有错则修测试并写明证据；行为未定义则先定契约。目标是可信基线，不是隐藏既有红灯。

## 4. P1：完成聊天媒体的真实交付验收

### B1. 回复归属、完成判定与媒体独占回复

**待验证风险：** 引擎的聊天事件过滤、message_done 完成判定与仅媒体回复，需要使用真实事件形态核对。当前取件测试中部分使用模拟 stream_chat，不能代替引擎原始事件测试。

拟议覆盖：

- 文本加图片、仅图片、仅视频、多附件。
- 同一媒体出现在 presentation、tool_done、message_done 中的重复事件。
- 非当前 node/device 的媒体或完成事件，不得串入当前回复。
- 有媒体但没有文本时，区分明确正常结束、上游拒绝、断线和 idle 截断。
- 不把“收到过部分文本/媒体”一概当作完整成功。

验收：原始事件夹具经过实际引擎到驱动，再到 HTTP 响应；正常完成与部分失败有明确可区分结果。

### B2. 失败、预算与取消

拟议工作：

- 明确连接、等待生成、附件下载、存储分别如何占用总预算。
- 将下载失败、超时、存储失败统一映射为可识别的接口错误。
- 流式已经发送文字或附件后再失败时，保留已发生事实，并输出错误，不能以正常 stop 掩盖。
- 客户端取消后关闭生成器，取消本次取件，并释放账号锁/租用。
- 定义部分成功附件的保留与过期策略，避免失败请求无限留存文件。
- 核对累计附件数量和字节预算，而不仅是单文件上限。

验收：失败不返回空附件冒充成功；取消不遗留占用；磁盘错误不静默；可清楚区分“生成失败”与“生成成功但交付失败”。

### B3. 上游取件验收

推荐由轻到重执行，属于未来实施计划：

1. 优先使用用户已有且仍有效的媒体路径，验证读取、保存、下载及哈希，不额外生成。
2. 已有路径不可用时，先区分过期、会话失效、路径变化或协议变化。
3. 必须验证生成到交付全链路时，再安排最小图片样本并记录实际消耗；视频在图片链路稳定后单独安排。
4. 记录输入、事件归属、成品大小/类型、存储 token、下载哈希和阶段耗时；隐藏凭据。

分支：

- **取件成功、下载一致：** 可证明交付链有效，但仍不代表生成阶段已验证。
- **取件失败：** 在协议/会话层定位，暂不推进客户端美化。
- **生成成功、下载失败：** 作为交付故障处理，避免自动重复生成。

### B4. Relay 兼容性

契约维持：非流式 message.media；流式 delta.media；纯文本响应保持原样。

逐层比较 bridge 直连响应、relay 输出和客户端收到的结果。

| 分支 | 判断依据 | 后续方向 |
| --- | --- | --- |
| relay 保留字段 | 流式与非流式均完整保留附件数组 | 进入客户端展示验收 |
| relay 只保留非流式字段 | SSE 字段被过滤或重组 | 定位 relay 序列化边界，补透传或明确该版本限制 |
| relay 丢弃扩展字段 | bridge 有 media，relay 没有 | 优先修 relay；必要时增加明确的兼容模式 |
| URL 可见但不可下载 | 外部地址、路径前缀或认证方式不匹配 | 修地址和认证衔接，不改成携带长期密钥的链接 |
| 暂时没有 relay 环境 | 无法取得实际版本与配置 | 保留“未验收”，不虚构兼容结论 |

兼容模式候选是普通文本附件提示/链接或独立附件查询接口，须先明确调用方需求。不要默认回退为浏览器直接渲染的 Markdown 图片，也不要把大体积 base64 塞进聊天正文。

### B5. 客户端显示与下载

拟议体验：图片预览、视频播放、下载按钮、失败提示、过期提示。

- 客户端鉴权下载，再使用 media[].mime 创建适当类型的 blob URL。
- 下载响应保留 octet-stream + nosniff 约定，不靠 Content-Type 猜媒体种类。
- 页面切换或媒体替换时回收 object URL，避免内存泄漏。
- 验证相对 URL、MUSE_PUBLIC_BASE、反向代理路径前缀与跨域配置。
- 视频大文件结合 Range 行为验证；不要假定一次性下载整个视频就是最终方案。
- 没有附件时不出现空白卡片；附件失败时仍保留可读文本。

验收：实际目标客户端能展示/下载；错误 key、过期 token、断网、Range 请求有可理解的结果。

## 5. P2：运维观测、资源管理和发布

### C1. 从状态快照升级为可解释指标

healthz 中 accounts/refs 表示池内状态，不是命中率，也不能单独证明连接健康或已经发生复用。

候选指标：命中/未命中次数、未命中原因、握手次数、重连次数、回收次数、活跃租用、媒体取件/存储/下载失败数、各阶段耗时。

分支：单机部署优先结构化日志和内部统计；有现成监控再输出指标接口。日志不包含 Cookie、Bearer key 或完整用户提示词；公开健康接口与管理诊断接口分开考虑。

验收：一次慢请求能区分等待账号、握手、上游生成、取件或下载问题；无需仅凭总耗时推断。

### C2. 媒体容量与清理

- 核对现有过期清理的调用位置和触发方式，避免重复实现。
- 定义单附件、单回合及总磁盘容量限制。
- 明确正在下载文件与清理竞争的处理方式。
- 定义删除、过期与部分成功保留策略；客户端能区分附件已过期和生成从未成功。
- 同一实例多 key 是否共享媒体可见性，需要明确产品边界；Bearer 校验本身不等于按用户隔离。

### C3. 形成可审查发布候选

- 清点全部已修改和未跟踪文件，按暖池、聊天媒体、其他既有功能分组。
- 去除文档中未经证明的断言、含混时刻和过时行号。
- 统一说明默认开关、必要配置、媒体扩展字段及已知限制。
- 根据实际目标环境验证依赖、启动、停止和恢复。
- 发布前保存当前可运行版本的回退依据；无用户指令不提交或推送。

发布门槛：可信测试基线；P0 生命周期不变量通过；至少一条明确记录的媒体交付验收；relay/客户端覆盖范围有说明；回滚不会破坏现有账号数据与媒体文件。

## 6. P3：可选能力分支与启动条件

| 分支 | 启动条件 | 建议范围 | 当前决定 |
| --- | --- | --- | --- |
| 浏览器聊天媒体提取 | 实际仍依赖浏览器驱动且有丢附件需求 | 使用同一 media 契约，核对 DOM 与成品关联 | 排在协议交付稳定之后 |
| Space 导出错误与状态体验 | 有具体失败样本或客户端需求 | 保留 upstream code/message，明确等待/失败/过期 | 可独立小步推进 |
| 会话唤醒与续期 | 有可复现 unavailable/缺失 vm_id 情况 | 先恢复状态链，再考虑自动恢复 | 先收证据，不盲改 |
| TLS 指纹兼容 | 现有传输出现可复现、与指纹有关的阻断 | 限定受影响路径并评估依赖与维护成本 | 按需，不因单次 403 就归因 |
| /media/raw/workspace | fs.read 已无法满足明确需求 | 比较传输可靠性、鉴权和取件成本 | 暂不替换现有 fs.read |
| dyi.export | 用户确实需要账号数据备份/迁移 | 独立导出任务、下载预算、进度与存储 | 不与 Space/画布导出混名 |
| 同账号并发 fan-out | 串行成为已测量瓶颈且上游语义允许 | 完成归属、游标、取消与背压设计 | 当前不做 |
| 多进程扩展 | 单进程容量达到实际瓶颈 | 分布式账号占用与会话归属 | 不假设进程内锁能跨进程生效 |
| 协议注册/外部资产链路 | 明确的新需求与独立范围 | 另立项目评估依赖和成本 | 不纳入本路线主线 |

## 8. 每批次的交付模板

每批次结束都回答下面七项：

1. 具体问题和目标行为是什么？
2. 修改了哪些组件，是否改变公开契约？
3. 哪些不变量和边界被验证？
4. 证据是源码、离线测试、活网测试，还是尚未验证的假设？
5. 哪些失败仍存在，它们是否阻止该批次交付？
6. 当前运行服务是否已加载这批修改？
7. 下一步进入哪一个分支，触发依据是什么？

   `proxy["server"]`，于是返回 `None`，HTTP 与 WS **双双静默直连**——三条链路
   其实都没用代理，走的是同一条被墙直连。**产品代码三处构造均正确**
   （`protocol_driver.py:115`、`protocol_hub.py:242`、`muse_spaces.py:607` 统一
   `{"server": proxy}`），故**产品从未受影响**，错的只是排障脚本。按契约修正后：

   | 检查项 | 修正前 | 修正后 |
   | --- | --- | --- |
   | `/api/hatch/token`（真实 `build_headers`） | 403（实为直连） | **200，取到 token/notary** |
   | `connect()` | `ConnectionResetError` | **成功 5.80s / 4.75s（两次）** |
   | 活网 chat | 504 | **200/14.33s、200/3.11s（暖池命中）** |

   另两条被误读的细节：`/api/hatch/token` 的 403 来自**残缺请求头**（缺仓库
   `build_headers` 的 `Origin`/`Referer`/`Sec-Fetch-*`），不是出口受限；`/api/session`
   的真实字段在**顶层**（`vm_id`/`endpoint_url`/`vm_name`/`vm_state`），
   `cvm_eligibility.defaultVm` 是空的，照它取 `vmAddress` 会得到空串。
   关于 notary 的 per-VM 子域疑点：restriction 确实写
   `hostname:<vm_id>.metaaivm.com`，但**上游没有收紧**——LB 入口 101 + Noise msg2
   （166B）+ msg3 + split 全通，per-VM 子域反而 TLS 直接失败。故
   `use_endpoint_host=False` 保持默认，无需改动。
   **教训（写进流程）**：排障探针必须与产品同契约，`proxy` 一律
   `{"server": ...}`；探针报"多链路一致失败"时，先证明**代理真的被用上了**
   （在 opener 里回读 kwargs），再下"上游故障"的结论。
